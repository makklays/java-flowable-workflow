
15 золотых правил 'Clean Code'

1. Названия — это важно
Хорошие имена делают код самодокументируемым.
Имя должно отражать суть:
calculateSalary(), а не doWork().
Переменные и методы — в нижнем верблюжьем регистре (camelCase), классы — в верхнем (PascalCase).
Не сокращай: employeeCount, а не empCnt.
Избегай бесполезных слов: Data, Info, Manager.
2. Маленькие методы
Каждый метод должен делать только одну вещь и делать её хорошо.
Если метод длиннее 10–20 строк — подумай, можно ли его разделить.
Название метода должно описывать что он делает, а не как.
Метод с побочными эффектами — почти всегда признак грязного кода.
3. Не возвращай null
Вместо null:
Возвращай Optional<T> — если значение может отсутствовать.
Возвращай Collections.emptyList() или Collections.emptyMap() — для коллекций.
4. Одна ответственность (Single Responsibility Principle)
Каждый класс должен иметь только одну причину для изменения.
Если класс: и обращается к БД, и форматирует отчёт, и отправляет email — значит, нарушен SRP.
5. Избегай дублирования кода
Дублирование — зло.
Общие куски выноси в отдельные методы или утилитные классы.
Используй шаблоны проектирования (Strategy, Template Method и т.п.), если повтор логики сложный.
6. Пиши читаемый код, а не умный
Код читают чаще, чем пишут.
Выбирай простоту, а не “красивые трюки”.
Пиши так, чтобы даже новичок понял логику.
7. Комментарии — только там, где нужно
Код должен быть самодокументируемым.
Комментарии нужны, если: объясняют почему, а не что; содержат контекст решения; предупреждают о возможных проблемах.
8. Минимизируй область видимости переменных
Делай переменные, поля и методы максимально приватными (private).
Чем меньше область видимости — тем меньше шансов на баги.
Используй final, если значение не должно меняться.
9. Обрабатывай исключения правильно
Обрабатывай, где можешь исправить ситуацию.
Логируй с контекстом (log.error("Ошибка при чтении файла: {}", filename, e);)
10. Пиши тесты
Unit-тесты — часть чистого кода. Тесты должны быть простыми и читаемыми. Один тест — один сценарий. Используй понятные названия.
11. Чистая архитектура и зависимости
Разделяй слои: контроллеры, сервисы, репозитории. Внедряй зависимости через конструктор (Dependency Injection).
12. Используй константы и enum, а не “магические” значения
Плохо: if (status == 3)
Хорошо: if (status == Status.ACTIVE)
13. Форматирование и стиль — важны
Придерживайся единого стиля (Google Style, Sun Style, Checkstyle).
Отступы, пробелы, скобки — читаемость важнее вкуса.
Один логический блок — один абзац кода.
14. Избегай преждевременной оптимизации
“Сначала заставь код работать, потом — быстро, потом — красиво.”
Не оптимизируй то, что не измерил.
15. Пиши код так, будто после тебя его будет сопровождать психопат
Это цитата из Clean Code — и она передаёт суть:
делай так, чтобы любой человек мог легко понять и поддерживать твой код.

Правила для Java-кода

Используй читаемые имена для переменных, методов и классов (userRepository, calculateTotalPrice()).
Методы должны быть короткими и делать одно дело.
Избегай глобальных переменных и состояния, если оно не нужно.
Всегда закрывай ресурсы (try-with-resources).
Используй Optional вместо null.
Коллекции — всегда с дженериками (List<String> а не List).
Старайся делать поля private final, если они не должны меняться.
Логируй ошибки, но не глуши исключения (catch (Exception e) { log.error(e); } вместо пустого catch).
Не злоупотребляй статическими методами — они мешают тестированию.
Всегда пиши юнит-тесты для ключевой логики.

Архитектурные принципы

Hexagonal / Clean Architecture — ядро не должно зависеть от фреймворков.
DTO, Entity, Service, Controller — чёткое разделение слоёв.
Dependency Injection — внедрение зависимостей через конструкторы (а не new).
Avoid God Objects — избегай классов, которые “знают всё и делают всё”.
Configuration externalization — настройки должны быть вне кода (application.yml).

Принципы проектирования и архитектуры
🔹 SOLID (пять основных принципов ООП)

S – Single Responsibility Principle (SRP)
Каждый класс должен иметь только одну причину для изменения.
→ Один класс — одна ответственность.

O – Open/Closed Principle (OCP)
Классы должны быть открыты для расширения, но закрыты для модификации.
→ Добавляем функциональность через наследование или композицию, не ломая старый код.

L – Liskov Substitution Principle (LSP)
Объекты подклассов должны быть взаимозаменяемы с объектами родительского класса.
→ Наследование не должно ломать поведение базового типа.

I – Interface Segregation Principle (ISP)
Лучше несколько мелких интерфейсов, чем один “толстый”.
→ Не заставляй классы реализовывать ненужные методы.

D – Dependency Inversion Principle (DIP)
Модули верхнего уровня не должны зависеть от модулей нижнего уровня.
→ Зависит от абстракций, а не от реализаций.

Принципы кода и практики

DRY (Don’t Repeat Yourself) — не дублируй код, выноси общее в методы/классы.
KISS (Keep It Simple, Stupid) — решение должно быть максимально простым.
YAGNI (You Aren’t Gonna Need It) — не добавляй функционал “на будущее”.
Composition over Inheritance — предпочитай композицию наследованию.
Fail Fast — выбрасывай исключения как можно раньше, не тащи ошибку дальше.
Law of Demeter (Принцип наименьшего знания) — “не разговаривай с незнакомцами” (класс должен знать как можно меньше о других классах).
Separation of Concerns (Разделение ответственностей) — UI, бизнес-логика и доступ к данным должны быть изолированы.

Общие принципы тестирования

- AAA (Arrange, Act, Assert) — структура теста: подготовка, действие, проверка.
Каждый тест состоит из трёх частей:
// Arrange
User user = new User("Alice", 25);
UserService service = new UserService();

// Act
boolean result = service.isAdult(user);

// Assert
assertTrue(result);

- Изолированность — тесты не должны зависеть друг от друга.
- Повторяемость — тесты должны давать одинаковый результат при каждом запуске.
- Покрытие — стремись к высокому покрытию кода тестами, но не жертвуй качеством ради количества.
- Mocking — используй моки для изоляции тестируемого кода от внешних зависимостей.
- Тесты должны быть быстрыми — медленные тесты тормозят разработку.

Рекомендации по рефакторингу

Идентифицируй “код запахи” (code smells) — длинные методы, дублирование, большие классы.
Используй маленькие шаги — рефакторь по одному изменению за раз.
Пиши тесты перед рефакторингом — чтобы убедиться, что поведение не изменилось.
Применяй шаблоны проектирования — для улучшения структуры кода.
Документируй изменения — чтобы команда понимала, что и почему было изменено.
