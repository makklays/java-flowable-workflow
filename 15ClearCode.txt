
15 золотых правил 'Clean Code'

1. Названия — это важно
Хорошие имена делают код самодокументируемым.
Имя должно отражать суть:
calculateSalary(), а не doWork().
Переменные и методы — в нижнем верблюжьем регистре (camelCase), классы — в верхнем (PascalCase).
Не сокращай: employeeCount, а не empCnt.
Избегай бесполезных слов: Data, Info, Manager.
2. Маленькие методы
Каждый метод должен делать только одну вещь и делать её хорошо.
Если метод длиннее 10–20 строк — подумай, можно ли его разделить.
Название метода должно описывать что он делает, а не как.
Метод с побочными эффектами — почти всегда признак грязного кода.
3. Не возвращай null
Вместо null:
Возвращай Optional<T> — если значение может отсутствовать.
Возвращай Collections.emptyList() или Collections.emptyMap() — для коллекций.
4. Одна ответственность (Single Responsibility Principle)
Каждый класс должен иметь только одну причину для изменения.
Если класс: и обращается к БД, и форматирует отчёт, и отправляет email — значит, нарушен SRP.
5. Избегай дублирования кода
Дублирование — зло.
Общие куски выноси в отдельные методы или утилитные классы.
Используй шаблоны проектирования (Strategy, Template Method и т.п.), если повтор логики сложный.
6. Пиши читаемый код, а не умный
Код читают чаще, чем пишут.
Выбирай простоту, а не “красивые трюки”.
Пиши так, чтобы даже новичок понял логику.
7. Комментарии — только там, где нужно
Код должен быть самодокументируемым.
Комментарии нужны, если: объясняют почему, а не что; содержат контекст решения; предупреждают о возможных проблемах.
8. Минимизируй область видимости переменных
Делай переменные, поля и методы максимально приватными (private).
Чем меньше область видимости — тем меньше шансов на баги.
Используй final, если значение не должно меняться.
9. Обрабатывай исключения правильно
Обрабатывай, где можешь исправить ситуацию.
Логируй с контекстом (log.error("Ошибка при чтении файла: {}", filename, e);)
10. Пиши тесты
Unit-тесты — часть чистого кода. Тесты должны быть простыми и читаемыми. Один тест — один сценарий. Используй понятные названия.
11. Чистая архитектура и зависимости
Разделяй слои: контроллеры, сервисы, репозитории. Внедряй зависимости через конструктор (Dependency Injection).
12. Используй константы и enum, а не “магические” значения
Плохо: if (status == 3)
Хорошо: if (status == Status.ACTIVE)
13. Форматирование и стиль — важны
Придерживайся единого стиля (Google Style, Sun Style, Checkstyle).
Отступы, пробелы, скобки — читаемость важнее вкуса.
Один логический блок — один абзац кода.
14. Избегай преждевременной оптимизации
“Сначала заставь код работать, потом — быстро, потом — красиво.”
Не оптимизируй то, что не измерил.
15. Пиши код так, будто после тебя его будет сопровождать психопат
Это цитата из Clean Code — и она передаёт суть:
делай так, чтобы любой человек мог легко понять и поддерживать твой код.
